## 4. Media economy policy

### Resolution tiers

| Display role | Default generation | Maximum source role | Current Seedance 2.0 quote reference |
|---|---:|---|---:|
| Small in-layout ambient slot | 480p, 5–6s | approximately one-third viewport | 15–18 credits |
| Prominent half-width scene | 720p, 5–6s | approximately half viewport | 22.5–27 credits |
| Wide non-hero scene | 720p, up to 8s | wide but below the fold | up to 36 credits |
| Full-viewport founder hero | 1080p only after locked keyframes | LCP/full-screen | quote must be shown before approval |

Quotes are provider state, not permanent pricing. Re-query before every batch.

### Hard cost controls

1. No generation without the complete pre-generation approval card defined below.
2. One candidate per approved motion batch by default.
3. No speculative variants and no hidden automatic retry.
4. Non-hero video budget ceiling: 27 credits per candidate unless separately approved.
5. Default motion duration: 5–6 seconds; 8–10 seconds only when narrative timing demonstrably requires it.
6. Use standard bitrate for generation. Optimize locally after selection.
7. Generate audio only when explicitly required; About V3 defaults to silent video.
8. Reuse locked posters and stills for mobile/reduced-motion states instead of generating duplicate videos.
9. Do not upscale a small display slot merely because the model supports 4K.
10. Stop the media phase when the section communicates clearly; visual novelty is not a reason for another paid pass.

### Mandatory pre-generation approval card

Before every external image or video generation, Apollo must show one self-contained approval card and then stop. The card is required even when the broader media family or completion plan was previously approved.

The card must contain:

1. **Stable asset ID and name** — for example, `AV3-03-ARRIVAL-PLATE`.
2. **Page placement** — exact section number/title and whether the asset is full-screen, half-width, small in-layout media, poster, mobile source, or reduced-motion fallback.
3. **Narrative role** — what the visitor should understand because this asset exists and why locked stills/browser motion alone are insufficient.
4. **Browser relationship** — what is generated into the media and what remains live HTML/CSS/GSAP. Generated media must not absorb interface work that belongs in code.
5. **Exact outputs** — candidate count, format, aspect ratio, pixel resolution, duration/frame rate when applicable, audio state, and required responsive variants.
6. **Exact model and provider** — including a clear disclosure when a requested model such as Sora is unavailable and a fallback is proposed.
7. **Reference files and their roles** — identity authority, environment authority, start frame, end frame, continuity reference, or composition-only reference.
8. **Exact final prompt** — verbatim, not a summary. If the provider uses separate negative constraints or parameters, show those verbatim too.
9. **Exclusions and truth boundary** — prohibited identities, transformations, claims, generated text, client outcomes, or private system details.
10. **Acceptance checks** — the observable conditions required for the asset to be selectable.
11. **Fallback if rejected** — still/CSS/GSAP alternative or a revised batch; never assume an automatic retry.
12. **Fresh provider quote** — exact credits for the stated settings, remaining account balance before submission, and the configured cost ceiling.

Apollo must end the card with one exact approval phrase such as `approve AV3-03-ARRIVAL-PLATE v1`. A response approving a plan, section, or vague “all remaining media” does not authorize submission unless it clearly approves the displayed prompt and quoted configuration. Any change to the prompt, model, references, candidate count, duration, resolution, audio, or price invalidates the approval and requires a new card.

```text
MODEL: Higgsfield Seedance 2.0

PROMPT (verbatim): "..."
CONSTRAINTS (verbatim): "..."
ACCEPTANCE: ...
FALLBACK: ...

```

## 6. Technical architecture

### Framework decision

Keep the existing Next.js/React/GSAP/Lenis stack. Add no new animation framework and no WebGL dependency for About V3.

### Rendering boundary

- Keep route metadata, content, section structure, evidence labels, and most media markup server-rendered.
- Use one scoped client motion shell for page-level GSAP coordination.
- Split complex interactive units into bounded client components: opening state machine, orchestration atlas, proof comparison, controlled video, and inquiry form.
- Reuse `components/motion/gsap.ts`, the existing Lenis ticker, `HeaderZone`, tokens, and form infrastructure.
- Do not turn the full page into a client component.

### Motion rules

- `useGSAP()` with a root scope and automatic cleanup.
- `gsap.matchMedia()` for desktop/tablet/mobile/reduced motion.
- Create ScrollTriggers in document order; refresh only after real layout changes.
- Animate transforms, opacity, clip-path/masks, and SVG stroke state; avoid animated width/height/top/left when transforms can express the same result.
- Maximum two pinned desktop chapters: opening split and one explanatory chapter if testing proves it useful. No pinning on mobile.
- Physical video actions play autonomously forward. Scroll may enter/exit states but never controls the video playhead.
- Pause offscreen video and when the document is hidden. Permit only one active video.
- Keep essential meaning and controls in the DOM, not inside generated media.

### Media delivery

- Use explicit aspect-ratio boxes to prevent layout shift.
- `preload="none"` or `metadata` below the fold; load near view or on intent.
- Full-width hero may preload metadata/poster only until playback is imminent.
- Serve MP4 first; create WebM only after a video is locked and local tooling is available.
- Use `next/image` or `<picture>` with art-directed mobile sources for stills.
- Optimize copies into `public/media/about-v3/`; retain masters and generation records under `.olympus/`.
- Target small clips below approximately 1.5–2.5 MB where visual quality permits; never allow multiple autoplay downloads above the fold.

## 9. Acceptance and stop conditions

The page is ready for Gate C only when:

- all ten sections communicate the approved narrative;
- every production media item is locked, rights/provenance recorded, and correctly cropped;
- no fake Marija, invented proof, client result, metric, or unlabelled placeholder appears;
- desktop and mobile flows are readable without animation;
- generated physical action is never reverse-scrubbed;
- reduced motion uses stable posters and immediate completed states;
- only one video can play and below-fold video is not eagerly downloaded;
- browser console/runtime, keyboard order, focus, contrast, overflow, 200% zoom, and responsive states are verified;
- build/lint pass or unrelated pre-existing failures are documented precisely;
- the inquiry form performs one real provider-confirmed delivery;
- the user explicitly grants Gate C.

## 10. Recommended decision

Approve this unified plan with **implementation allowed to begin using clearly labelled development placeholders for identity-blocked sections**, while keeping every paid generation behind its own quote-and-approval gate. This lets the browser experience prove which videos are actually necessary before spending more credits.
